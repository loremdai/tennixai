# T96 Player and Historical Results Field Audit

Status: complete (2026-09-24; implementation `b4acb8b`). Implementation and field evidence are recorded in the linked [T95–T96 matrix](../../research/2026-09-24-tennixai-t95-match-field-integrity-matrix.md).

## Goal

Audit player-facing data that T95 did not cover: ranking snapshots, player profiles/season records, player result pages, and the history/H2H query results (`PlayerResults`, `HeadToHead`, `HeadToHeadResult`). Trace API-Tennis fields through mapping, service, storage/read models, REST, chat, and UI. Fix only defects proved by focused regressions; document unknown provider semantics rather than guessing.

## Evidence and scope

- Official [API-Tennis REST documentation](https://api-tennis.com/documentation) documents standings fields, player-profile fields, and the three `get_H2H` lists. It does not define H2H ordering/count limits, standings source timestamps, or a comparison period for its movement field. ATP/WTA official ranking sources document the actual tour rank and points context; never infer an undocumented supplier field from a similarly named profile-season field.
- The same API-Tennis docs represent `player_country` as a country name and include `scores` separately from `event_final_result`; the implementation uses the maintained [pycountry ISO registry](https://github.com/pycountry/pycountry) for standard names/codes, explicit aliases for tennis-specific conventions, and [FlagCDN](https://flagcdn.com/) for remote flag images rather than bundled hand-drawn assets.
- Inspect provider DTOs/mappers, service/cache, player-directory persistence/read models, REST schemas/routes, chat output, and player ranking/profile/history UI. Record every field and its exact source, units, ordering/identity, empty/unknown meaning, freshness, truncation, and consumer in the T95 matrix.
- Additional official references: [ATP rankings FAQ](https://www.atptour.com/Rankings/Rankings-FAQ.aspx), [WTA rankings explanation](https://www.wtatennis.com/rankings-explained). API-Tennis fixture `timezone` is documented as the timezone for returned data; the product timezone is now Beijing (`Asia/Shanghai`), including player-result dates.
- Confirmed by RED regressions and fixed (25 observable behaviors across the audit and Beijing-time pass): H2H availability checked only `meetings`, not all three capped arrays; raw H2H lists could hit the provider cap but fall below it after unmappable rows were dropped; yesterday history could hit the 10-row cap but claim complete; a successful empty season was marked unavailable; an empty/filtered ranking page could invent request-time `as_of`; a profile picked the provider's first upcoming row rather than the earliest; doubles leaked into singles profile/current-match results and Home Chat's yesterday/last/recent result scopes; profile season default and result-season validation used UTC year; the selector omitted years without season aggregates; an unknown winner was treated as a loss in the API and UI; result date and displayed year came from UTC; standings `ranking_date` used UTC day; initial profile season used the browser's local year; player age used the UTC calendar; GMT fixture date filters could omit matches in the first Beijing hours of a season; undated season results could appear complete; the P3 market/workbench clock followed browser timezone; unmapped ISO country names/codes hid nationalities and flags; player history dropped an available final set count when detailed score rows were empty; and Home Chat could claim a complete history scope despite an undated returned singles result. The Beijing-time follow-up and independent review added four findings beyond the initial 17; the final country/score follow-up added two; review added the chat-history doubles gap, and a later completeness review added the undated Chat history gap.

## Steps

2. Make minimal service/model/view-model changes: mark capped history partial; distinguish successful empty season results from unavailable data; preserve real ranking snapshot time (or null when none exists); select the earliest eligible singles match without relying on supplier row order; consistently use the configured Beijing calendar for service, standings snapshot dates, frontend year selection, age, display, and season-boundary filtering; provide the full five-season selector independently of available statistics; preserve unknown winner/date semantics; normalize ordinary provider nationality names through an ISO country registry with tennis-specific aliases; show `sets_won` as a clearly labeled history fallback only when no per-set game scores are usable; and apply the same singles-only history contract to Chat's yesterday/last/recent results.

5. Run focused service/provider/API/chat/player-directory/player-profile tests, the deterministic backend suite where possible, the player-view-model Vitest test and TypeScript check, Ruff on changed Python files, and `git diff --check`.
